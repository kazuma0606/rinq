# RINQ v4.0 設計検討（Gemini 指摘・拡張案）

**作成日**: 2026-03-26
**対象**: `versions/v4/spec.md`

## 1. 指摘事項（設計の懸念点と改善提案）

### D2: `#[diagnostic]` メンテナンスの自動化
型ステート（`Initial`, `Filtered`, `Sorted` 等）ごとにサポートするメソッドとエラーメッセージを定義するのは非常に強力ですが、メソッドが増えるにつれて「どの状態にどのメッセージを出すか」の定義が重複・散散する恐れがあります。
- **提案**: `SupportsSelect` のようなトレイトを定義する際に、メッセージも一括で定義できる内部用マクロ（例: `define_state_constraint!`）を用意し、ボイラープレートを削減すべきです。

### E6: `unfold` のランタイム安全装置
無限シーケンスの `collect()` は Rust の型システムでは防げません。
- **提案**: `debug_assertions` 有効時のみ、`unfold` のイテレータに内部カウンタを持たせ、例えば 1,000,000 回（あるいは環境変数で設定可能）を超えた場合にパニックまたは警告ログを出す「セーフティネット」の導入を検討してください。

### H1: `Arc` ソースのコピーコストの明示
`from_arc` の実装案で `(*source).clone()` となっていますが、これは `Vec<T>` 全体のコピーを伴います。
- **指摘**: ユーザーが「`Arc` なので参照カウントが増えるだけ（安価）」と誤認する可能性があります。ドキュメントに「この操作は O(N) のコピーを伴う」ことを明記するか、将来的に `QueryBuilder` がライフタイムを持てるようにして `&[T]` を直接扱えるようにする道を残すべきです。

### G4: `rinq-syntax` の Hygiene（衛生性）
`query!` マクロ内で `let` バインディングをサポートする場合、ユーザーが定義した変数名とマクロ内部で使用する変数名が衝突するリスクがあります。
- **指摘**: `proc-macro2` の `Span::mixed_site()` を適切に使用し、マクロ展開後の変数がユーザーコードの変数と衝突しないよう厳密なテストが必要です。

## 2. 拡張案（さらなる進化のためのアイデア）

### 拡張案 1: `tracing` クレートとの統合（Observability）
`rinq_explain!` は独自の標準出力を行いますが、現代の Rust エコシステムでは `tracing` クレートが標準です。
- **内容**: `feature = "tracing"` が有効な場合、各ステップ（`where_`, `order_by` 等）を `tracing::span` で囲むようにします。これにより、エンジニアは `tokio-console` や Jaeger などの分散トレーシングツールでクエリのボトルネックを可視化できるようになります。

### 拡張案 2: `#[derive(Queryable)]` によるバリデーション自動生成
`rinq-derive` でフィールドアクセサを作る際、検証ルールも宣言できると強力です。
- **内容**:
  ```rust
  #[derive(Queryable)]
  pub struct User {
      #[queryable(range(18..120))] // 年齢制限
      pub age: u32,
      #[queryable(regex = r"^\w+@\w+\.\w+$")] // メルアド形式
      pub email: String,
  }
  ```
  このように記述すると、`Age::validate(val)` や `Email::validate(val)` が自動生成され、`ValidationExt` とシームレスに連携できるようになります。

### 拡張案 3: SIMD 最適化の導入 (rinq-stats)
統計演算において、大量の数値を扱う場合にパフォーマンスの差別化要因になります。
- **内容**: `rinq-stats` の `sum`, `average`, `exponential_moving_average` 等の内部実装で、`std::simd` (nightly) または `packed_simd` クレートを利用した高速化オプションを提供します。

### 拡張案 4: `pipe_async` のプレビュー導入
v5 の非同期対応を前に、`pipe` の非同期版を実験的に導入します。
- **内容**: `async_pipe` メソッドを追加し、外部の非同期関数（DB への問い合わせや外部 API 呼び出し）をチェーンの途中に挿入し、その結果でクエリを継続できるようにします。

### 拡張案 5: Fluent エラーハンドリング
現在のバリデーションは、エラー時に即座に結果を返さないスタイルに見受けられます。
- **内容**: `try_collect()` のようなメソッドを追加し、バリデーションエラーがあった場合に `Result<Vec<T>, Vec<ValidationError>>` を返せるようにします。
